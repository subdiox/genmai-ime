# CLAUDE.md — genmai-ime

genmai is a Japanese input method for macOS: a conversion engine ported to Swift from Mozc
(https://github.com/google/mozc, 3.35.6354) plus optional on-device AI conversion with the genmai language model
(Core ML). Runtime, UI and data generation are all Swift; the C++ Mozc in `Vendor/mozc` is only the source of the
dictionary data and the reference ("oracle") for parity tests. User-facing overview: `README.md`. Per-file
porting state: `PORTING_STATUS.md`.

Code, comments and docs are in English.

## Reference

- `Vendor/mozc` — git submodule, google/mozc pinned at **0136c35 (3.35.6354)**. Port from this exact revision.
- **Data sets are built natively**: `Tools/build_data.sh [--oss|--mock] [--verify]` runs `genmai-datagen` (Swift
  ports of every upstream data generator, `Sources/GenmaiDataGen`) and writes `Data/genmai.data` /
  `Data/mock_genmai.data` (git-ignored), byte-identical to the upstream Bazel outputs. The zip code CSVs and the
  usage dictionary are downloaded (pinned, sha256-checked) into `Data/external/` (git-ignored).
- **Extended data set (not in Mozc)**: `Tools/build_data.sh --extended` also writes `Data/genmai_extended.data`, the
  set the IME bundles (`Tools/make_ime_bundle.sh`, release workflow): the OSS set + an extra dictionary
  (`genmai-datagen extra-dictionary`, `GenExtraDictionary.swift`; ~67k proper nouns the OSS dictionary lacks:
  municipality / town names of KEN_ALL.CSV, SudachiDict 20261015 small_lex + core_lex proper nouns (person names
  from small_lex only; core's ~180k mostly rare names flood common readings), no addresses (prefecture / city +
  more), Mozc proper noun ids, cost = the OSS dictionary's 90th percentile for the id). `Data/genmai.data` stays
  Mozc's (parity tests). SudachiDict is Apache 2.0: `Tools/assets/credits_extended.html` is added to the bundled
  credits. Foundation's NFKC leaves half-width voiced kana decomposed (ﾍﾞ → ヘ + U+3099): NFC after it.
- `Tools/build_oracle.sh` builds the reference C++ tools (converter_main, immutable_converter_main) and the Bazel
  data sets with bazelisk (`Tools/bin/`, git-ignored). Only needed to regenerate parity fixtures.
- `Tools/oracle.sh [flags] < commands` runs the C++ converter_main (`s <reading>` = start conversion,
  `p <reading>` = prediction, `suggest`, `commit`, `resize`, ...; see `converter/converter_main.cc`). Its output
  (segments, candidates with cost / scost / wcost / lid / rid / attributes / segbdd) is the parity target: the
  Swift CLI `genmai-engine` must print the same text for the same commands.

## Package layout

The upstream engine directories reference each other (converter ↔ prediction / rewriter / engine, data_manager →
converter headers, dictionary → request), so they share one module with a subfolder per upstream directory.
Layers: GenmaiProtocol / GenmaiBase / GenmaiStorage → GenmaiCore → GenmaiSession → app.

| Swift module (folder) | upstream source | notes |
|---|---|---|
| GenmaiProtocol | protocol/*.proto, data_manager/dataset.proto, prediction/user_history_predictor.proto | generated by protoc-gen-swift (see its README.md), then renamed (`Genmai_Commands_*`, package `genmai.*`); do not edit by hand |
| GenmaiBase | base/ | platform code (win32, android, process spawning) replaced by Foundation |
| GenmaiStorage | storage/ | |
| GenmaiCore/DataManager | data_manager/ | reads `Data/genmai.data` (memory-mapped; the data format and its magic number are upstream's) |
| GenmaiCore/Config, Request, Composer, Transliteration, Dictionary, Converter, Rewriter (all 31), Prediction, Engine | same names | |
| GenmaiSession | session/, usage_stats/ | |
| genmai-engine | converter_main | CLI printing the oracle's format, for parity |
| GenmaiClient, GenmaiRenderer, GenmaiGUI, GenmaiMac, GenmaiIME, GenmaiApp, GenmaiUninstaller | client/, renderer/, gui/, mac/ | InputMethodKit app; SwiftUI UI |

| GenmaiClient/AIConversion, GenmaiAIClient | — | the IME's AI conversion hook and its genmai augmenter |

Naming: every module, type and user-visible string is "Genmai". Upstream names remain where they identify upstream
things: `Vendor/mozc` paths, Bazel targets and output names, the data set magic number, and `// Port of
mozc/src/...` provenance comments.

## Porting rules

1. **Faithful port, not a rewrite.** Same algorithms, constants, thresholds, iteration order and tie-breaking as
   the C++ code, so outputs match the oracle bit for bit. One Swift file per C++ .cc/.h pair, same base name in
   UpperCamelCase (`immutable_converter.cc` → `ImmutableConverter.swift`), starting with
   `// Port of mozc/src/converter/immutable_converter.{h,cc} (3.35.6354).` Keep upstream comments that explain
   behavior. C++ `CamelCase` methods → Swift `lowerCamelCase`; enums and constants keep their meaning.
2. **Strings and byte offsets.** The C++ uses UTF-8 `std::string` and many algorithms index by **byte** (lattice
   positions, key lengths, `substr`). Use Swift `String` for values but compute positions with `.utf8` counts and
   slice via UTF-8 (helpers in GenmaiBase). Never replace a byte offset with a Character count. Binary data
   (dictionary, connection matrix, LOUDS, serialized arrays) is read through `Span<UInt8>` of a memory-mapped
   `Data` (`data.span`; `loadLittleEndian(_:at:)` etc. in GenmaiBase/ByteSpan.swift); no copies of big sections.
8. **Safe Swift only.** No unsafe APIs (`Unsafe*Pointer`, `withUnsafe*`, `unsafeBitCast`, `nonisolated(unsafe)`,
   `@unchecked Sendable`, `assumingMemoryBound`) where a safe alternative exists: `Span` / `RawSpan` /
   `MutableSpan`, `Mutex`, Sendable value types. No force unwrapping (`!`, `try!`, `as!`, implicitly unwrapped
   optionals). Swift `Regex`, not `NSRegularExpression`. Prefer the latest Swift / Apple APIs. Where an unsafe API
   is unavoidable (C APIs such as mmap or Authorization Services), keep it to one small wrapper with a comment.
3. **absl / std replacements.** `absl::flat_hash_map` → `Dictionary` only where iteration order does not affect
   output; `std::sort` is not stable — where ties matter, match what the C++ produces. `absl::Status(Or)` →
   `throws`. Fingerprint / hash functions must be bit-exact (user history keys are persisted).
4. **Swift 6, strict concurrency, macOS 15+.** No `DispatchQueue`; use `async/await`, actors or `Mutex`. Locks are
   **`Mutex` only** (`import Synchronization`, preferably `Mutex<State>`); no `NSLock` / `NSRecursiveLock` /
   `OSAllocatedUnfairLock`, no `_unsafeLock`. `Mutex` is not recursive. **No thread-blocking waits**
   (`NSCondition`, semaphores, sleep-polling): a C++ `Wait()` becomes `async` and awaits the background work
   (GenmaiBase `TaskManager`, an actor on its own executor); synchronous paths such as
   `SessionHandler.evalCommand` never wait. `ExistentialAny` is enabled. C++ interfaces become protocols; mocks become test doubles.
   **Pitfall:** if a protocol requirement has a default in an extension and a base class does not implement it, a
   subclass's method is not called through `any Protocol`. In callback hierarchies the base class implements every
   requirement and subclasses `override`.
5. **Tests.** Swift Testing. Port the C++ `*_test.cc` of every ported file (same names in lowerCamelCase). Test
   data lives in `Vendor/mozc/src/data/test/...`; locate the repository root from `#filePath`. Tests that need
   `Data/genmai.data` or the AI model skip with a clear message when it is missing.
6. **Parity tests** (converter and above): oracle outputs are stored under `Tests/Fixtures/oracle/` so tests run
   without Bazel.
7. Parallel work: give each worker its own folders and its own build directory (`--build-path .build-<name>`).

## AI conversion (GenmaiAI)

The genmai models decode the conversion from the reading by beam search on Core ML (Neural Engine). Two models, each
its own Hugging Face repository with its own releases (git tags vX.Y.Z), same tokenizer, prompt format and file
layout (CC BY-SA 4.0): **genmai-310M** ([subdiox/genmai-310M](https://huggingface.co/subdiox/genmai-310M), "medium",
the default; GPT-2, character-level, 24 layers, 1024 dim) and **genmai-90M**
([subdiox/genmai-90M](https://huggingface.co/subdiox/genmai-90M), "small", distilled from genmai-310M into
zenz-v3.2-small; 12 layers, 768 dim). Release **v1.0.0** of each: `config.json` (`genmai_prompt_format` zenzlc),
`tokenizer.json` / `tokenizer_config.json`, the fp32 `model.safetensors` (HF layout, for transformers and the Core ML
conversion) and **`model-coreml.zip`** (what the IME installs). The Swift decoder is a port of the Python reference
decoder of the training code (genmai research repo); an MLX decoder existed before 1.0.0 and was removed (Core ML
needs a fraction of the memory: genmai-310M 80–140 MB vs. 1–2.7 GB).

- `GenmaiTokenizer` (byte-level BPE from tokenizer.json, ids identical to the HF GPT2Tokenizer; fixtures in
  `Tests/Fixtures/genmai/`), `GenmaiPrompt` (format `zenzlc`: left context first, up to 500 characters, then the
  katakana reading; lengths in **Unicode scalars**), `GenmaiCoreMLModel` (the decoder, below), the shared beam
  search (`GenmaiDecoder` / `GenmaiSearch`: `genBatch` / `extend` / `convert` / `split` at 40-character chunks,
  `score`), `GenmaiConverter` (actor owning the model; `workLock` serializes and measures the work of all
  converters), `GenmaiIncrementalConverter` (converts finished chunks while typing).
- The model is not bundled. `AIModelSize` (small / medium) names the repositories and the memory AI conversion adds
  with each (`memoryMegabytes`: 90 / 150, shown in the AI tab's model picker). `GenmaiModelRelease.latest(repository:)`
  (GenmaiClient/AIConversion) asks the Hugging Face API for the repository's tags (`/api/models/<repository>/refs`),
  takes the vX.Y.Z tags newest first and returns the first whose config.json this IME can run (`isCompatible`: gpt2,
  `genmai_prompt_format` zenzlc or absent) and that has config.json, tokenizer.json and `model-coreml.zip`, with
  their sizes and checksums from `/api/models/.../tree/<tag>` (LFS sha256 for the archive, git blob sha1 for the
  small files). **Nothing about a release is hard-coded**: publishing a new tag is enough, unless it needs decoder
  changes (then give it another prompt format / model type, or another archive name for a Core ML format older IMEs
  cannot run, so they skip it). `AIModelInstaller.install(release)` downloads the files (kept in
  `~/Library/Caches/Genmai/download/<repo>@<tag>` until the install succeeds), verifies the checksums and the config,
  extracts the archive with `/usr/bin/ditto -x -k` (Foundation has no zip API; awaited through the process's
  termination handler), checks the format in `genmai_coreml.json`, compiles each package (`MLModel.compileModel`) and
  replaces config.json / tokenizer.json / `genmai*.mlmodelc` / `genmai_coreml.json` / `genmai_model.json` (installed
  repository and release) one at a time (other files are left alone). The setting `model_size` (AI tab "Model":
  Small / Medium) picks the model; choosing the other one looks up its latest release and offers its download
  (`AIModelStatus.needsInstall`: another model or a newer release). `AIModelInstaller.uninstall` removes only those
  files (and the directory if nothing else is left). Front ends: the settings tab "AI" (looks up the latest release
  when shown; Download / Update when it is newer than the installed one, with progress and cancel; "Remove Model…"
  after a confirmation; both send RELOAD and `GenmaiAugmenter` reloads because `AIModelStatus.identity` — size and
  mtime of the model files — changed), `genmai-cli install [--size small|medium] [--tag vX.Y.Z]` and
  `Tools/prepare_genmai_model.sh [--size small]`. Tests use `$GENMAI_MODEL_DIR`, else
  `~/Library/Application Support/Genmai/model`, and skip without a Core ML model there.
- **New model release:** convert the fp32 checkpoint with `Tools/coreml/genmai_coreml.py` (below; it writes
  `model-coreml.zip`), check it (`genmai-cli eval --model <out dir>`, `GENMAI_MODEL_DIR=<out dir> swift test --filter
  GenmaiAITests`), upload `model-coreml.zip` next to config.json, tokenizer.json and model.safetensors, and tag.
- `genmai-cli`: `install`, `convert`, `eval [--incremental] [--every-key] [--draft] [--no-kv-reuse]` (per-item latency
  and the process footprint), `compare`, `session-eval` (below); `--model DIR` and `--units ane|cpu|gpu|all` pick the
  model and Core ML's compute units. `propose`, `rescore`, `dict-hints`: see "Dictionary in the AI conversion".

### Core ML decoder (Neural Engine)

`GenmaiCoreMLModel` implements `genBatch` and `logProbs` of the protocol `GenmaiDecoder` (GenmaiDecoder.swift); `gen` /
`extend` / `convert` / `score`, the drafts (`GenmaiDraftStore`: verification `accept`, only single-context searches
store a draft), max_new, truncation and the result lists (`GenmaiSearch`) are shared code. Compared with the MLX
decoder it replaced (genmai-90M, M4 Pro): top-1 identical 101/101 daily, 199/200 AJIMEE, 27/28 hard (n-best lists
64–82 % identical: fp16).

- Model directory: `genmai.mlpackage` (or compiled `genmai.mlmodelc`; `genmai_0` / `genmai_1` with chunks),
  `genmai_coreml.json` (format `genmai-coreml-1`; static shapes: prompt slots P, output steps S, rows B, prefill chunk
  C; optional `chunks`), tokenizer.json, config.json. A multifunction package, functions `prefill` (C prompt tokens at
  a slot offset; log-probs after each) and `decode` (B rows, one token each), sharing one `MLState`: prompt KV (P
  slots, the last prompt; a new prompt prefills from its first differing token) and output KV (S × B slots, row r's
  step-t token at t·B + r; rows attend to their ancestors through a mask, so beam reordering copies nothing). The
  decode step writes its output slots by a blend (`state * keep + onehot @ k`): a dynamic slice update of a state runs
  on the CPU and splits the ANE graph (6.8 vs 3.3 ms per step). Every function must use every state (prefill reads
  the output states × 0), or conversion fails. Drafts are prefilled after the prompt; the accepted tokens' KV stays in
  the prompt slots. `logProbs` (scoring a given output) prefills the prompt + the text and reads the rows.
- **Chunks:** a package with the weights of more than ~12 layers of genmai-310M (≥ ~200 MB) fails to load on the
  Neural Engine, with a misleading error ("`functionName` must be nil unless the model type is ML Program"; the same
  package loads on the CPU). Not the number or size of states (merged K/V states, smaller P / S: same failure), and
  splitting the functions inside one package does not help. genmai-310M is therefore split into `chunks` = 2
  packages `genmai_0` / `genmai_1` (layers 0–11 / 12–23), each with `prefill` / `decode` for its layers and its own
  state; chunk 0 takes the tokens, chunk 1 the `hidden` output (fp16), the last returns the log-probs.
- **fp16 range:** genmai-310M's residual stream reaches ~81k and one head of layer 1 has attention logits up to
  ~500k (an attention sink), beyond fp16 (65504): NaN. The converter reparametrizes exactly: `--residual-scale 0.25`
  (embeddings and attention / MLP output projections × 0.25, layer norm eps × 1/16; layer norms are scale-invariant,
  the head keeps the unscaled embeddings) and `--score-scale 256` (logits computed / 256 via the query weights, row
  max subtracted, × 256 before the softmax).
- The B rows hold one search, so `genBatch` searches its contexts one after another. `extend` passes a
  `GenmaiSearchBound` (hypothesis texts / scores, beams): a search stops once all its rows are below the `beams`-th best
  distinct text found so far, which does not change the result (log-probs only decrease). Drafts with several contexts
  are verified for all first (the accepted prefix is the minimum), then the searches run.
- The packages are made by `Tools/coreml/genmai_coreml.py <HF dir> <out dir> [--chunks N] [--residual-scale R]
  [--score-scale C]` (coremltools 9, torch GPT-2 with per-layer `(H, slots, D)` fp16 states, int8 per-channel linear
  weights, iOS 18 target; pinned versions in `Tools/coreml/requirements.txt`); genmai-90M without options,
  genmai-310M with `--chunks 2 --residual-scale 0.25 --score-scale 256`; it also writes `model-coreml.zip`
  (`genmai_coreml.json` + the packages). P = 256, S = 64, B = 5, C = 32. genmai-90M: 82 MB archive, decode 4 ms per
  step on the ANE, footprint 46–90 MB, first load compiles for the ANE (~18 s, cached by the system). genmai-310M:
  283 MB archive, footprint 80–140 MB, first load ~22 s; plain conversion daily median 113 ms; conversion key with
  every-key speculation + drafts (`eval --incremental --every-key --draft`) median 30 / 39 ms, p90 102 / 156 ms
  (daily / AJIMEE; the MLX decoder: 19 / 21, 51 / 90 ms); `eval` top-1 daily 94.1 / AJIMEE 93.0 / hard 78.6 %. The same
  package gave garbage on `.cpuAndGPU` (unexplained); ANE and CPU are correct.
- Tests: `GenmaiSearchTests` (shared helpers), `GenmaiConverterTests` / `GenmaiCoreMLModelTests` (need a Core ML
  model in `$GENMAI_MODEL_DIR` or the IME's model directory).

### AI conversion in the IME

Optional and **off by default**; off, the IME converts exactly like the engine alone (all parity fixtures
unchanged; the hook only forwards). GenmaiCore and GenmaiSession contain no AI code.

- **Hook points (GenmaiClient/AIConversion):** `SessionHandlerBackend(aiHook:)` wraps the engine in
  `AugmentedEngine`, whose converter is `AugmentingConverter`: it forwards `ConverterInterface` and calls
  `AIConversionHook.augmentConversion` after `startConversion`, `augmentSuggestion` after `startPrediction` /
  `startPredictionWithPreviousSuggestion`, and reports commits from `finishConversion`. `evalCommand` calls
  `willEvaluate` / `didEvaluate` around `SessionHandler.evalCommand` (active session, left context, background
  conversion of the composition).
- **The conversion key never blocks.** `augmentConversion` only uses a result that is already there
  (`ConversionAugmenter.readyResult`). A result still in flight is awaited *before* the key is evaluated:
  `AIConversionHook.conversionWait(for:)` returns a task bounded by `timeout_ms` (default 300; on timeout the
  conversion is cancelled, not awaited). `GenmaiInputController.aiConversionGate` reports the key as handled,
  queues it and the keys typed meanwhile and sends them in order afterwards; any other converter request first
  flushes the queue. In-process clients use `hook.sendKey(_:via:)`.
- **Background conversion (`GenmaiAugmenter`)**, after every composition change: (1) exact conversion of the
  finished chunks, (2) speculative conversion of the whole composition with draft-and-verify, latest wins (at most
  one running and one waiting), (3) after a 400 ms pause an exact conversion that restores the full n-best list.
  Results are cached (8). The reading is the preedit without pending romaji letters (full-width in the default
  preedit form: かいｓ → かい); a pending ｎ counts as ん, like the engine's conversion query.
- **Decoding speed-ups (`GenmaiCoreMLModel`):** *prompt KV reuse* — the KV of the last prompt stays in the prompt
  slots and a new prompt prefills from its first differing token, so only the new kana are prefilled.
  *Draft-and-verify* (speculation only) — the previous best output is appended to the prompt and verified in the
  prefill; the longest prefix whose tokens are each the argmax by ≥ 2 log-prob is accepted and the beam search
  continues after it, continuing only the best hypothesis of earlier chunks (same top-1 as without it on the eval
  sets). `warmup` runs one conversion at load time.
- **Memory:** the model's packages are memory-mapped by Core ML; the IME's footprint grows by about 90 MB (small) /
  150 MB (medium) at most while converting. Turning AI conversion off releases the converter.
- **Readings and forms:** the model gets the conversion key in the *preedit* character form ("？", "（", as in its
  training data); its output gets the *conversion* character form (`CharacterFormManager`).
- **Merging (`AIConversionMerger`, `AIConversionAligner`):** if the AI top-1 differs from the engine's top, the AI
  text is aligned with the engine's segments by reading (kana and symbols are anchors; kanji / digit / Latin runs
  read 1–8 characters each), cut at the segment boundaries (preferring the engine's segments, pieces that are
  engine candidates, early kana); segments whose boundary falls inside a kanji run are merged with
  `resizeSegments` (the boundary is not learned). Each AI piece goes to the top of its segment (description "AI",
  POS ids from an engine candidate with the same functional suffix, RERANKED so that committing it is learned like a
  user choice); the AI alternatives follow. The AI top wins over learned tops (user segment history; the learned
  value stays right below it); only a piece the user replaced after an AI conversion (`rejected`) keeps the
  engine's top. **User dictionary words win over the AI:** an AI piece that does not contain one of the user
  dictionary candidates of its segments is not used; those segments keep Mozc's result with the user's word on top
  (`keptUserWords` in the debug log).
- **AI result in the suggestion window:** `augmentSuggestion` computes what the conversion key would show (an
  engine conversion of a copy of the segments + the same merge) and puts it first, so the first suggestion equals
  the conversion result. Until the result for the current composition is ready, the last AI suggestion stays on
  top, extended by the kana typed since (`keepLastSuggestion`), so the row does not flicker. When a result arrives
  after the key was answered, `GenmaiInputController.aiSuggestionUpdate` re-requests the suggestion with
  MOVE_CURSOR to the current position (re-runs `suggest` without changing the composition) and updates only the
  candidate window; stale refreshes (another output meanwhile, queued keys, different preedit) are ignored.
- **Candidate window stability:** size and position change in one `setFrame`; `CandidatePlacement.keepSide` keeps
  the window above the preedit for the rest of a composition once it went there; unchanged lists are not redrawn.
- **Reading check (`AIReadingChecker`):** before merging (conversion and suggestion), AI candidates that cannot be
  read as the conversion key are dropped; the order is kept and if none passes the first stays. Lenient by design
  (one possible reading suffices; an exact reverse-conversion check lost correct answers): both sides are folded
  (NFKC, katakana → hiragana, voicing marks removed, small kana enlarged, ー / 〜 removed) and a DP reads the text
  with system dictionary words (reverse lookup on a second `SystemDictionary` built with the reverse lookup index in
  the background when AI is enabled, from `Engine.getDataManager()`), their one-character entries for single kanji,
  kana / symbols as themselves, wildcards for digit / Latin runs (+ one counter kanji) and kanji without entries, and
  one か / の / つ between two kanji. ~0.2 ms per candidate (release), results cached. Setting `reading_check`
  (default on, no UI); `session-eval --no-reading-check` compares; the debug log notes `unreadable=[...]`.
- **Left context:** IMK surrounding text up to 500 characters plus text committed in the session; reset on
  activation, RESET_CONTEXT or an empty preceding text. The model tends to copy the context: a wrong conversion
  committed earlier in the same field can be repeated.
- **Settings:** `<profile>/ai_conversion.json` (`AIConversionSettings`: `enabled`, `timeout_ms`, `candidates`,
  `model_directory`, `model_size`, `reading_check`, `dictionary_weight`, `dictionary_proposal_weight`, `debug_log`),
  edited in the settings tab "AI" and re-read on the reload notification. `model_directory`, `reading_check`, the
  dictionary weights and `debug_log` have no UI (development / diagnosis);
  the model folder is managed by the installer, so the AI tab shows only which model and release is installed.
- **Debug log (opt-in):** `"debug_log": true` appends one line per AI event to `<profile>/ai_debug.log` (rotated at
  8 MB): source (`ready` / `awaited` / `timeout` / `error` / `suggestion` / `refine`), reading, last 40 characters of
  context, latency, n-best and what was shown. **It contains the typed text**; turn it off after diagnosing.
- **Evaluation:** `genmai-cli session-eval [--timeout-ms N] [--settle none|chunks|idle] [--typing-ms N[,N]]
  [--space-delay-ms N] [--trace] [--errors] [--profile-copy DIR] [--debug-log] [--no-reading-check] [--out-dir D]
  <set.json>...` types each reading through `SessionHandlerBackend` with and without the hook (real-time typing with `--typing-ms`),
  presses the conversion key and reports accuracy, latency, where the result came from and the model's busy time
  per keystroke. `--trace` prints the suggestions per key including refreshes; `--profile-copy` runs on a copy of a
  user profile (never written). Results (genmai-310M 0.1.0 on the former MLX decoder, with the reading check, M4 Pro,
  120 ms per kana; "now" = key right after the last kana, "+1" = one interval later):

  | daily (101) / AJIMEE (200) | strict top-1 | key median / p90 | ready at key | timeouts |
  |---|---|---|---|---|
  | engine alone | 73 / 103 | 3 / 6 · 7 / 27 ms | | |
  | AI, now | 93 / 188 | 45 / 86 · 64 / 137 ms | 0 / 0 % | 0 / 1 |
  | AI, +1 | 93 / 188 | 11 / 16 · 19 / 57 ms | 100 / 90 % | 0 / 0 |

  The reading check drops 19–37 % of the AI candidates in these runs
  (speculative n-best lists of partial readings included), never a correct one; with `--settle chunks`
  (AJIMEE / daily / hard) it changes top-1 by 187 / 94 / 20 vs. 186 / 94 / 20 without it, at the same key latency.

- **Dictionary in the AI conversion (`AIDictionaryScorer`, setting `dictionary_weight`, default 0.2, no UI):** the
  model invents spellings for proper nouns it does not know (日下部町 → 草壁町, 西神吉 → 西換気) and used to override
  Mozc's correct ones (proper nouns of the Mozc dictionary: Mozc alone 96/110, with AI 58/110). The scorer computes
  the cost of the cheapest path through Mozc's lattice that produces exactly a text (system dictionary tokens +
  connection costs; uncovered kana / symbols 3000 each; nil if a kanji has no token). (1) `rerank` (in
  `GenmaiAugmenter.Core.convert`, before results are cached): among the AI candidates that differ from the top only
  in kanji (same `kanaSkeleton`: 晩ご飯 / 晩ごはん is style, left to the model), the best of model log-prob −
  weight × cost / 500 becomes the top. (2) **Proposals** (`dictionary_proposal_weight`, default 1.0): the model writes
  names it does not know in kana or with other kanji, and then the right spelling is not among its candidates at all.
  `AIDictionaryScorer.propose` takes the cheapest path through the lattice of the reading (`bestPath`: Mozc's
  conversion without rewriters; uncovered characters cost 10000 there, with 3000 a run of kana beat 西神吉) and, if
  it has a proper noun with kanji the AI's top lacks, proposes its text and the top with the noun written for its kana
  (アザミヒラ → 莇平). The augmenter scores the proposals with the model (`GenmaiDecoder.score`: log-probs of the text
  + EOS after the prompt, = the beam search's score; readings of one chunk only) and `rerank` holds a second round:
  its first-round winner against the proposals (AI candidates equal to one count as proposals), whatever their kana,
  with the proposal weight. (3) the merger keeps Mozc's text for a group of segments whose top is a proper noun
  (`PosMatcher.isUniqueNoun`) when the AI wrote its reading in kana where Mozc has kanji, or differs only in kanji and
  costs ≥ 2000 more (or is unreachable) (`keptDictionaryWords` in the debug log). A better dictionary thus improves
  the AI conversion. `genmai-cli rescore [--data FILE] [--weights ...] [--verbose] gen_*.json` replays (1) on `eval`
  n-best lists; `genmai-cli propose [--data FILE] [--weight W] [--proposal-weights W,...] <reading | set.json>...`
  shows the candidates, proposals, costs and scores of a reading, or the accuracy per proposal weight on a set
  (one-shot conversions, genmai-90M Core ML, extended data: proper nouns 220 / 110 sets 72 / 64 without proposals,
  110 / 81 at 1.0, 120 / 83 at 2.0; daily 94, AJIMEE 177, hard 22 up to 1.0, AJIMEE 176 from 1.5); `session-eval
  --dictionary-weight W --proposal-weight W` (defaults 0.2 / 1.0, settle chunks, genmai-90M Core ML, extended data:
  proper nouns 126 / 220 and 89 / 110 (without proposals 92 / 76, Mozc alone 134 / 96), daily 94, AJIMEE 176, hard 20,
  the same as without them; conversion key unchanged). Proper-noun eval sets (template sentences) live outside the
  repo.
- **Dictionary hints (for training; not used by the IME yet):** the next model is to get Mozc's view of the reading
  in its prompt and learn to take the dictionary's spelling of words it does not know. `AIDictionaryHinter` computes
  the hints: `segments` (Mozc's conversion, no user dictionary / learning) and `properNouns` (system dictionary proper
  nouns for parts of the reading the conversion lacks; ≥ 3 reading characters, ≥ 2 characters with a kanji, not
  inside a longer one's reading, at most 3). `genmai-cli dict-hints [--data FILE] [--jobs N] in.jsonl out.jsonl`
  writes them for training data (`{"id", "reading"}` lines → `{"id", "reading", "h1", "segments", "proper_nouns"}`;
  default data set `Data/genmai_extended.data`; ~750 readings / s on an M4 Pro). The training data's hints must come
  from this code, and the IME must compute them the same way once a model with the new prompt format exists.
- **Known model weaknesses:** readings that repeat one sound (きしゃのきしゃがきしゃできしゃした,
  にわにはにわにわとりがいる) map every occurrence to the same word or drop part of the reading; fine homophone
  distinctions and rare proper nouns.
- Tests: GenmaiClientTests (aligner, merger, settings, reading check, safetensors conversion, the hook in the real
  session layer with `FakeAugmenter`), GenmaiGUITests (AI tab, model installation with a fake installer),
  GenmaiMacTests (key queue, suggestion refresh), GenmaiRendererTests (`CandidatePlacement`), GenmaiAITests
  (tokenizer, decoding, KV reuse / draft vs. plain), GenmaiAIClientTests (model-backed speculation).

## GUI design (not in Mozc)

The windows keep Mozc's options and dialog logic (`ConfigDialogModel`, `DictionaryToolModel`, ...) but not its
Qt layouts. GenmaiApp is a SwiftUI `App` with one `Window` scene per process (id = the mode, so SwiftUI keeps a
frame per mode), so the windows get the system's chrome; startup checks (mode, run level, singleton, welcome
marker) run in `GenmaiApplication.init`, closing the window quits. the settings window is a sidebar of panes (General / Input / Conversion / Suggestions / AI / Privacy /
Updates), each starting with a System Settings-like header (icon, name, summary; no toolbar title), whose edits are saved automatically (`savesChangesAutomatically`, 300 ms after the last edit and on
close; no OK / Cancel / Apply), the candidate window a Liquid Glass panel (window background at 70 % underneath for legibility; metrics in
`CandidateDesign`, the infolist a card layout in `InfolistDesign` instead of renderer_style.textproto), the
dictionary tool a `NavigationSplitView` with an SF Symbols toolbar and a
search field, the About window a centered icon / version / links layout, the editor sheets (key bindings, romaji
table) `EditorSheet` + `TableEditorBox` (+ / − / ⋯ under the table, keys shown as ⌃⇧A; GenericTableEditor.swift),
the error dialog an alert-style window, the uninstaller one window with confirm / removing / done / failed states,
and the installer has welcome / conclusion pages (Tools/installer/Resources). Wording that differs from Mozc's
translations lives in `Base/GenmaiStrings.swift` (looked up by `tr` before Mozc's) or in a per-window strings
table; use "…" and "ユーザー".

## App updates and releases (not in Mozc)

- The Genmai app (product GenmaiApp) is bundled as `Genmai.app/Contents/Resources/Genmai.app` with executable
  `Genmai` (`GenmaiConst.kGenmaiApp`), so the Dock, the app switcher and Activity Monitor show "Genmai". The user
  facing copyright is "Copyright © 2026 subdiox"; Mozc's license notices stay in `credits_en.html` (linked from the
  About dialog; required by Mozc's BSD license). Google-only features (usage statistics upload, uninstall survey)
  were removed.
- Icons (Tools/make_icon.swift → Tools/assets): the input method's 玄 icon, the app's with a gear badge, the
  uninstaller's with a trash badge; same glyph (Hiragino Mincho ProN W6), colors and shape. Each bundle gets an
  Icon Composer `Assets.car` (`CFBundleIconName`, macOS 26+: the system draws shape and glass) and an `.icns` on
  the macOS icon grid (`CFBundleIconFile`, macOS 15).
- Logging out: a first installation shows up in the input menu only after the user logs out and in (the installer
  pages and the welcome window say so); updates take effect at once (postinstall restarts GenmaiIME). After
  uninstalling, logging out is enough (the uninstaller offers "Log Out Now"; no restart).
- Install location: Installer offers "all users" (`/Library/Input Methods`, the default; Installer asks for an
  administrator) or "me only" (`~/Library/Input Methods`, no administrator rights) — distribution.xml `domains`;
  the scripts derive the domain from `$2` and run their user-level steps with `sudo -u` only when they run as root.
  An installation for all users removes a per-user copy (same bundle id). In-app updates install where Genmai is:
  per user with `installer -target CurrentUserHomeDirectory` (no window, no rights), for all users by opening
  Installer (`GenmaiPackageInstaller`).
- Uninstaller (GenmaiUninstaller, `UninstallGenmai.app`) lives in `Genmai.app/Contents/Resources` (built by
  Tools/make_ime_bundle.sh) and is opened from the settings (General › Uninstall Genmai…); nothing is installed into
  /Applications (0.1.0 did; preinstall and the uninstaller remove that folder). Items outside the home folder are
  removed as root after the system authorization dialog (Authorization Services, Touch ID) through
  AuthorizationExecuteWithPrivileges (deprecated, looked up with dlsym, as Mozc / Google Japanese Input do; the
  only replacement, an SMAppService daemon, needs approval in System Settings first); a per-user installation is
  removed without rights. The user data kinds the user checks go too (AI model + caches checked by default; user
  dictionary, learning data, settings kept by default).
- CI: `.github/workflows/ci.yml` builds every product and runs `swift test` on each push to main and on pull
  requests (release build with `-enable-testing`: debug tests took 45 minutes on the runner; code that must hold in
  debug builds only is not checked there) (macos-26 runner, the same Xcode as releases; the data sets are built and cached, model tests skip).
  The local Xcode can be newer than the runner's: code that compiles here can still fail there.
- Releases: GitHub releases of subdiox/genmai-ime, tag vX.Y.Z (= `kProductVersion`; the first public release is
  1.0.0, earlier releases were removed), asset `Genmai.pkg` (the update check takes any `.pkg`), so
  `releases/latest/download/Genmai.pkg` is always the newest package.
  Normally made by the GitHub Actions workflow `.github/workflows/release.yml`: bump `kProductVersion`, commit, push
  the tag `vX.Y.Z`; the workflow (macos-26 runner, newest Xcode ≥ 26) builds the data set and the
  package and creates the release (a manual run only builds and keeps the package as an artifact).
  `Tools/make_release.sh [--publish]` does the same locally. The package installs where the user chose (see
  "Install location") and opens the
  welcome window (app screen `welcome`, `GenmaiGUI/Welcome`: how to switch to Genmai, "Turn On AI Conversion" =
  model download + `enabled`) once per user (marker `<profile>/welcome_shown`).
- Updates (GenmaiClient/Update): `GenmaiAppRelease.latest` (GitHub API `/repos/.../releases`: highest vX.Y.Z, no
  drafts / pre-releases, with a .pkg asset; size + SHA-256 `digest`), `GenmaiUpdater.download` (shared
  `FileDownload`, also used by the model installer), `GenmaiUpdateSettings` (`<profile>/update.json`:
  `automatic_check` (default on), `last_check`, `skipped_version`). The IME (`GenmaiMac/GenmaiUpdateChecker`) checks
  once a day and posts a notification that opens the app screen `update_dialog`; the settings have
  the "Updates" pane (`GenmaiUpdateModel`). The downloaded package has no quarantine attribute and is installed
  where Genmai is (`GenmaiPackageInstaller`).
